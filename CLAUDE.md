# UFot - Football Match Tracker

## Project Overview
A personal web app to log football matches watched, browse them in a feed, and view statistics. Designed for scalability — future plans include multi-user support with accounts.

## Tech Stack
- **Framework**: Next.js 16 (App Router, TypeScript, Turbopack)
- **Database**: SQLite via `better-sqlite3` (direct, no ORM)
- **Styling**: Tailwind CSS v4
- **Node.js**: v24 (installed at `/c/Program Files/nodejs`)

## Key Decisions
- **No Prisma**: Prisma 7 driver adapter system had compatibility issues on Windows ARM64. Using `better-sqlite3` directly instead.
- **No Google Fonts**: Turbopack had fetch issues with Google Fonts. Using system fonts.
- **`serverExternalPackages`**: `better-sqlite3` is listed in `next.config.ts` to handle native module loading.
- **`export const dynamic = "force-dynamic"`** on pages that read from DB to prevent caching stale data.
- Database auto-creates tables on first import of `db.ts`. Migrations (e.g. adding columns) use `PRAGMA table_info` checks.
- **Design system**: Dark theme with `#c9ff00` (electric lime) accent. Custom CSS variables defined in `globals.css` and registered in Tailwind's `@theme` block (`accent`, `card`, `surface`, `muted`, etc.).
- **External API**: **API-Football v3** (api-sports.io). Auth: `x-apisports-key` header, env var `API_FOOTBALL_KEY`. Free tier = 100 req/day, all endpoints. Covers ~1,200 leagues including Eliteserien.
- **Team crests**: Stored as URLs (`home_crest`, `away_crest` columns). Displayed via `<img>` tags with a placeholder shield SVG for manually-entered matches. Remote images allowed from `crests.football-data.org` (legacy rows) and `media.api-sports.io` (new) in `next.config.ts`.
- **Timezone-aware dates**: The football API proxy accepts a `timeZone` param from the client (via `Intl.DateTimeFormat`) and forwards it to `/fixtures?date=...&timezone=...`. API-Football returns fixtures already bucketed in the requested timezone, so no ±1-day widening is needed.
- **Add match flow**: Browse-first — `/add` auto-loads today's finished matches grouped by competition (sorted by popularity via `competition-order.ts`, which keys on API-Football numeric league IDs). Date is driven by prev/next-day arrows with a calendar picker as secondary; a "Today" shortcut appears once the user navigates away. Clicking a fixture **does NOT write to the DB** — it navigates to `/fixtures/[externalId]` (with the summary stashed in `sessionStorage` under `fixture:<id>` for instant render, falling back to `GET /api/football/fixtures/[id]` on deep-link/refresh). That preview page shows a prominent "Did you watch this?" card with the `WatchIntervalEditor`; only on **Mark as watched** is the row POSTed to `/api/matches` and the user redirected to `/matches/[id]`. Cancel returns to `/add`. If a fixture is already in the DB, `MatchBrowser` links straight to `/matches/[id]` instead. Collapsible manual form remains as fallback for matches not in the API.
- **Watch intervals**: Stored as JSON `[[start, end], ...]` in `watch_intervals` column (default `[[0,90]]`). Editable at add-time and from the match detail page. Stats page shows **Total Minutes** and **Matches Watched** — the old "Equivalent Matches" (minutes / 90) metric was removed everywhere in favor of plain Minutes + Matches.
- **Match details (eager + rescue)**: `external_match_id` + `external_source` stored on add via browse. Hydration (goals with `scorer_id`/`assist_id`, subs with in/out IDs, lineups with per-player IDs and grid positions, formations, team IDs, and yellow/red cards — via `/fixtures/events` + `/fixtures/lineups` + `/fixtures?id=`) happens at **three** moments, all sharing `hydrateMatchDetails(matchId)` in `src/lib/match-hydration.ts`: (1) **POST-time eager fetch** in `/api/matches` right after insert — this was added because relying on the match-detail page's `useEffect` to trigger the fetch left rows stuck at `details_fetched=0` whenever the user bailed before the page loaded, and stats/player aggregation skips `details_fetched=0` rows so matches were invisible; (2) **Lazy on match-detail view** via `/api/matches/[id]/details` for rows that slipped through; (3) **Stats-page rescue** via `hydratePendingMatches(5)` — backfills up to 5 per load (= 15 requests) so transient POST-time failures self-heal. The helper is best-effort: on failure it leaves `details_fetched=0` so the next caller retries. `saveMatchDetails` is **idempotent** — it DELETEs detail rows for the match before inserting, so racing hydration paths (POST + rescue) can't produce duplicates. Cached in `match_goals`, `match_substitutions`, `match_lineups`, `match_cards` tables plus `matches.home_formation` / `away_formation` / `home_team_id` / `away_team_id`. Manual entries and legacy football-data.org rows show "not available". **Completeness check (`details_complete`)**: `details_fetched=1` only records that hydration *ran*, not that the payload was full. API-Football publishes `/fixtures/lineups` and `/fixtures/events` asynchronously — a match hydrated immediately after final whistle can come back with empty lineups (Brann vs Aalesund 2026-04-22) or partial events (Senegal vs Morocco 2026-01-18 stored 1 of 3 goals). `saveMatchDetails` now sets `details_complete=1` only when both teams have ≥1 starter row AND the saved goal-event count is ≥ `home_score + away_score`. Formations and sub counts aren't checked because the API legitimately returns null formations and variable sub counts for valid matches. `getPendingHydrationIds` and `hydrateMatchDetails` both treat `details_complete=0` as "needs retry" while still marking `details_fetched=1` so partial data stays visible to stats during the retry window. `getMatchesWithDetails` keys on `details_fetched` (not completeness) so partial data isn't hidden. **Schema migrations**: use SQLite `user_version` bumps (currently at v10: v1=scorer/assist ids, v2=match_cards table, v3=wipe players cache after the `expandAbbreviatedName` fix so "Luke Paul Hoare Shaw" gets re-fetched as "Luke Shaw", v4=wipe again after teaching `expandAbbreviatedName` to keep the abbreviation when `firstname[0]` doesn't match the initial, v5=wipe after adding the `/players?id=X&season=Y` season-fallback, v6=wipe once more after `expandAbbreviatedName` learned to scan every word of firstname — Harry Maguire's firstname is "Jacob Harry", and scanning beyond the first word finds "Harry" matching the "H." initial; v7=delete `teams` rows where `national IS NULL` so the next enrichment pass re-fetches with the flag set; v8=`details_complete` column added and backfilled by re-checking lineup-presence + goals-vs-score for every existing api-football row; v9=referee + home/away coach columns added on `matches` and a `coaches` cache table introduced — flip `details_complete=0` for every existing api-football row so the rescue loop re-hydrates them and picks up coach/referee from `/fixtures/lineups`+`/fixtures?id=X` calls we were already making; v10=`fetchMatchDetails` now reads `fixture.venue.{id, name, city}` from the same `/fixtures?id=X` call and persists it via `saveMatchDetails` (with COALESCE so manually-set venues don't get overwritten). Targeted re-hydration: flip `details_complete=0` only for api-football rows where `venue_id IS NULL`, since the rest already have venue data and don't need to spend API budget). A previous `every-import` schema-drift block that wiped details when `home_formation IS NULL` or any sub had `player_in_id IS NULL` was **removed** — those are legitimate API nulls (API doesn't always know formation or substitute IDs), not drift signals. The block fired on every db.ts re-import and created an infinite re-fetch loop that kept specific matches (e.g. Norway vs Switzerland, Everton vs Man United) permanently invisible to stats. Use `user_version` bumps for one-shot migrations when the schema grows.
- **Pitch lineup visualization**: `<PitchLineup>` renders a horizontal pitch (home left, away right, mirrored) with aspect 3/2 and `maxHeight: 70vh` so it fits on screen without scrolling. Players placed by API-Football `grid` (`"row:col"`, row 1 = GK, higher rows toward midfield) with formation-string fallback (e.g. `"4-2-3-1"` → rows of 4, 2, 3, 1). Rows span nearly the full half (GK ~5% from endline, deepest row ~95% — so starters actually fill the pitch instead of clustering near the endline). **Away-half mirror**: within a row, the col→top mapping is reversed for `side === "away"` so that API col 1 (the team's own left, attacking their own goal) lands at the bottom of the screen when the away team attacks leftward. Without this flip both teams' LBs ended up on the screen top. Each starter shows a photo from `https://media.api-sports.io/football/players/{playerId}.png` (no API call — direct CDN), with initials fallback on `onError`. Shirt-number badge on photo. Clicking a player goes to `/players/{id}`; clicking a team header goes to `/teams/{id}`. **Per-player annotations** (via a `getAnnotations(player, side)` callback from `MatchDetailClient`): club crest **or** nationality flag under the photo (club wins when set — see national-team handling below), yellow/red card badge top-right, sub-off arrow top-left (with red-card/subbed-off → photo dimmed to 60%), and a small event line below the name showing a ball SVG for goals, boot SVG for assists (`BallIcon` / `BootIcon` — inline so they scale with dot size), plus `↓75'` for sub-off. **Badges live on a relative outer wrapper, not inside the `rounded-full overflow-hidden` photo circle** — otherwise the shirt number / card / sub-off badges get clipped by the circle and disappear. Goal/assist attribution matches by `player_id` first, falls back to name.
- **National-team pitches → club on dot**: The `teams` cache carries a `national` flag (API-Football `/teams?id=X` → `team.national`). The match-details API route detects `homeIsNational` / `awayIsNational`, and for starters on any national-team side it fetches `/transfers?player=X` (bounded to 25 new fetches per match view) and writes them to the `player_transfers` table. It then picks each player's most-recent non-national `team.in` row and returns a `playerClubs` map. `MatchDetailClient.getAnnotations` swaps nationality for club (logo + name + `/teams/{clubId}` link) on national-team sides; club-vs-club matches are unchanged. A dedicated `player_transfer_fetches` table records which players have been tried so empty-result fetches aren't retried forever.
- **Team & player profile pages**: `/teams/[teamId]` and `/players/[playerId]` aggregate watched matches. Team page shows W/D/L, Matches, GF/GA, goal diff, minutes, per-match result letters (W/D/L), a dedicated **Country** card below the header that links to `/countries/[code]` (lazy-fetched from the `teams` cache via `fetchTeamProfile` on profile load — separate card so the link target is unambiguous on national-team pages where the team name and country share the same label). National teams also show an accent-colored eyebrow above the team name with `National team · Men|Women · Senior|U-NN` (gender + age computed via `classifyNationalTeam(name)` — same helper used by the country page's two-column split) and an accent-tinted card border., plus a **Most Watched Players** card scoped to players from this team's side of each match (via `getTeamPlayers(teamId)` → `computePlayerStats({ onlyTeamId })`, reusing the same sortable/filterable `PlayerStatsTable`). `getTeamProfile` is now async because of the country lazy-fetch. **Un-watched teams still render**: when `mine.length === 0` the profile is built from the `teams` cache (with the same lazy `fetchTeamProfile` rescue) and returns zero-filled stats; the page replaces the players + matches sections with a "You haven't watched X yet" stub. `notFound()` only fires when the team can't be resolved at all (bad id with no cache + API miss). Player page shows a header with **Club / Nationality / Position / Shirt #** chips (position + shirt come from `/players/profiles` — the `players` cache table stores them), a stats grid of minutes/matches/goals/assists/yellows/reds, an Appearances list, and a **Club history** card rendered from `player_transfers` (fetched lazily via `getPlayerTransferHistory`).
- **Player identity unification**: Player stats and the player-profile page both first build a global `name → id` map across every match's lineups, goal/assist ids, sub in/out ids, and card player ids. `computePlayerStats.ensure(playerId, name)` resolves a name-only record to its canonical id when available, and if we find an existing `name:{name}` orphan when an id is now known it re-keys it to `id:{resolvedId}` (merging the two half-records). `getPlayerProfile(playerId)` accepts a lineup row as this player's appearance when either `lineup.player_id === playerId` *or* `lineup.player_id == null && knownNames.has(lineup.player_name)`. When a profile is requested for someone with no appearances, we no longer `notFound()` — the page falls back to the `players` cache header plus a "No watched appearances yet" line. Fixes both the "one match instead of two" undercount and the clickthrough 404s.
- **Substitutions + cards split**: On match detail, subs and cards each render in two columns (home left, away right) with a linked team header for each, so team ownership is immediately visible.
- **API-Football quirks**: For `type="subst"` events, `player` = player going OFF, `assist` = player coming ON. For `type="Goal"` events, `detail="Missed Penalty"` must be filtered out (not a scored goal). `detail` strings ("Normal Goal"/"Own Goal"/"Penalty") are mapped to UFot's stored types ("REGULAR"/"OWN_GOAL"/"PENALTY"). For `type="Card"` events, `detail` is matched case-insensitively: "Yellow Card" → `YELLOW`, "Second Yellow card" → `YELLOWRED`, "Red Card" → `RED`.
- **Player statistics**: Computes per-player minutes watched using interval overlap between player playing time (start to sub-out) and user's watch intervals. Goals/assists/yellows/reds only counted if the event minute falls within watch intervals. Each stat also carries **club** (team + crest + id from the player's most recent watched match) and **nationality** (name + ISO2 code). `PlayerStatsTable` has sortable Y and R columns. The player profile page (`/players/[playerId]`) shows total yellows/reds alongside minutes/matches/goals/assists, and flags per-appearance cards.
- **Player nationality (lazy-fetch)**: Nationalities are cached in a `players` table (`id, name, nationality, country_code, photo, position, shirt_number, fetched_at`). On each stats-page load, `enrichPlayerStatsWithNationality` fills from cache for all players and fetches up to 20 uncached ones via `/players/profiles?player=X` (1 req per player, bounded to respect 100/day). `position` + `shirt_number` ride along on the same fetch — the player page reads them directly from this cache for the header chips. Country-name → ISO2 lives in `country-codes.ts` (hardcoded common football nations, with UK home-nation codes `gb-eng`/`gb-sct`/`gb-wls`/`gb-nir`). Flag URLs use `flagcdn.com/{code}.svg` (not api-sports flags, which don't support home-nation subdivisions).
- **Team country + national flag (lazy-fetch)**: A `teams` table (`id, name, country, country_code, logo, national`) caches results from `/teams?id=X`. `enrichTeamRecordsWithCountry` (in `team-stats.ts`) fills from cache and fetches up to 20 uncached per stats-page visit; it now also propagates `national`. `isNational` / the national-team pitch path in the match-details API rely on the same table, fetching on demand for the two match teams when absent.
- **Competition logo + country (lazy-fetch)**: A `competitions` table (`id, name, country, country_code, logo, fetched_at`) caches results from `/leagues?id=X` via `fetchLeagueProfile`. The browse flow threads the fixture's `league.id` through `/fixtures/[externalId]` → `POST /api/matches` as `competitionId`, persisted on `matches.competition_id` so aggregation can group by league identity (with name fallback for manual-entry and legacy rows). `enrichCompetitionRecordsWithDetails` in `competition-stats.ts` fills from cache and fetches up to 20 uncached per stats-page visit — mirrors the teams pattern exactly. **Region overrides**: API-Football returns country `"World"` for every continental competition, which displays as a flagless "World" row. A `REGION_OVERRIDES` map in `competition-stats.ts` (league id → `{ country, countryCode: null }`) overlays the correct region at read time — not persisted so the map can grow without a cache wipe. Covers UEFA (Champions League, Europa League, Conference League, Euro, Nations League, Super Cup → "Europe"), AFCON → "Africa", AFC Asian Cup → "Asia", Copa America / Libertadores / Sudamericana → "South America", CONCACAF Gold Cup → "North America". `resolveCompetitionRegion(id, fallbackCountry, fallbackCode)` is used by the competition detail page; `enrichCompetitionRecordsWithDetails` applies the same override internally. `isRegionName` identifies region pseudo-countries; the stats table and the `/competitions/[id]` header render all regions as a non-linked pill with a globe SVG (no country flag — flagcdn has no continent flags, and the EU flag is politically distinct from UEFA so using it for Europe would be misleading).
- **Player transfers (lazy-fetch)**: `player_transfers` table stores one row per transfer (`player_id, transfer_date, type, team_in_id/name/logo, team_out_id/name/logo, fetched_at`, unique on `(player_id, transfer_date, team_in_id)`). A sibling `player_transfer_fetches` tracking table records players we've already tried, so empty results don't cause re-fetch storms. `fetchPlayerTransfers(playerId)` calls `/transfers?player={id}` and is invoked from two places: (1) the match-details route for national-team starters, and (2) `getPlayerTransferHistory(playerId)` on the player page for the Club History card. The player page prefers cache and only fetches when `hasFetchedPlayerTransfers` is false.
- **Gender filter on stats tables**: Every stats table (Teams, National Teams, Players, Competitions, Stadiums total + in-person, Coaches, Referees) carries a Men / Women / Total toggle above the existing filter input (`GenderToggle` in `TableUtils.tsx`). Each stat row is tagged with `gender: "men" | "women"`. For teams, gender comes directly from the team name via `classifyTeamGender` in `lib/gender.ts` — generalized version of `classifyNationalTeam`'s regex (trailing `" W"`, `" (W)"`, or `"Women"`). For derived entities (players, competitions, stadiums, coaches, referees) gender is the dominant side of their watched-match minutes — tracked per-entity in a `{ men, women }` tally during aggregation, then resolved to whichever has more minutes. `pickDefaultGender(matches)` picks the table's default: on `/stats` and full-table sub-pages it's the user's overall preference; on scoped pages (team/competition/country) it's derived from that entity's match set, so a women's-team page opens on Women instead of empty. Player-stats gender tally is keyed by stat object reference (not key string) because orphan-resolution moves stat objects between map keys (`name:X` → `id:N`); orphan merges fold the orphan's tally into the existing entry's.
- **Stats UI**: The `/stats` page has six overview cards (Matches Watched, Total Minutes, Total Goals Seen, Teams Watched, Players Watched, Competitions Watched) followed by three sortable tables in order **Teams → Players → Competitions**. All three default-sort by **Minutes desc**, with the **Minutes** column placed immediately left of **Matches**. Tables are paginated 10-per-page via a shared `usePagedRows` hook (`src/app/stats/_components/TableUtils.tsx`) with Prev/Next controls; the filter inputs still live inside Teams and Players (filtering resets pagination). Each card header has a **See all →** link to a dedicated full-table page (`/stats/teams`, `/stats/players`, `/stats/competitions`) that renders the complete sorted list unpaginated (`pageSize={null}`). Shared sort helpers (`HeaderButton`, `SortArrow`, `SortDir`) now live in `TableUtils.tsx` — numeric columns default to `desc`, strings to `asc`, active header shows a `▲/▼` glyph. All four stats tables (`TeamStatsTable`, `PlayerStatsTable`, `CompetitionStatsTable`, `StadiumStatsTable`) use `table-layout: fixed` with a `<colgroup>` (numeric columns get explicit Tailwind widths, the left-most text column is flex) so column widths stay constant across pagination / sort / filter. Text cells use `min-w-0 truncate` so long names clip with ellipsis inside the fixed cell instead of overflowing. **Row rank (`#` column)**: every stats table (Teams, Players, Competitions, Stadiums, Coaches, Referees) leads with a non-sortable `#` column showing the row's 1-based position in the current sort. `usePagedRows` returns a `startIndex` (= `(page - 1) * pageSize`, or 0 when unpaginated) so paged tables continue numbering across pages (page 2 of a 10/page table starts at 11). Numbering reflects the *current* sort and filter state — sorting by Y desc renders the player with most yellows as #1.
- **Universal click-through (entities → drill-down pages)**: Every team, player, competition, and country reference across the app is a navigation point. Tables (`TeamStatsTable`, `PlayerStatsTable`, `CompetitionStatsTable`) wrap the entity cell in a `<Link>` whenever the row carries the relevant id (teamId / playerId / competitionId / countryCode). Match-detail page links goal scorers, assist credits, and substitution in/out names via a small `PlayerName` helper, in addition to the bench/cards which already linked. The competition badge on `MatchCard` and the match-detail header is a sibling `<Link>` (the surrounding card was restructured so the badge is no longer nested inside the card-wide `<a>`, since nested anchors are invalid HTML). Appearance/match rows on `/teams/[id]` and `/players/[id]` are similarly split: the row is a plain `<div>`, with the score+date links separate from the team-name links, so each entity is independently clickable.
- **Competition page (`/competitions/[id]`)**: Server component that resolves the `competitions` cache row, filters `getMatchesWithDetails()` to that competition (id-first; legacy rows fall back to name match against the cached competition name so older manually-entered matches roll up correctly), then renders Most Watched Teams (`aggregateTeams` → `TeamStatsTable` unpaginated), Most Watched Players (`computePlayerStats` → `enrichPlayerStatsWithNationality` → `PlayerStatsTable` unpaginated), and a Matches Watched list. Header has logo + name + a country pill linking to `/countries/{code}`.
- **Country page (`/countries/[code]`)**: Server component, distinct from `/teams/{nationalTeamId}`. Header card carries a sky-blue **COUNTRY** eyebrow + sky-tinted card border so it's visually distinct from a national-team page (which uses an accent-lime eyebrow + border) — important because the team name and country name are identical for senior national teams. Resolves country name via `codeToCountryName(code)` (404 if unknown). Loads `getTeamsByCountryCode(code)` (split into clubs vs national teams), `getCompetitionsByCountryCode(code)`, and all matches with details. Renders four sections: **Clubs from country** (matches involving any non-national team from that country, then post-filtered to those teams), **Competitions from country** (id+name fallback filter), **Players from country** (nationality match across every watched match), and **Players in country competitions** (any nationality, but only matches whose competition belongs to that country). National teams from the country render as a dedicated **National teams** section above the four rollups, split into a two-column grid: **Men** on the left, **Women** on the right. Each column lists the senior team first then youth teams in descending age (U-23 → U-21 → U-19 → …). Gender is detected from the team name (`/\bwomen\b/`, `/\(w\)/`, or trailing ` W`); age from `/U-?(\d{1,2})/`. Every national team in the cache is shown — un-watched ones get a "not watched" pill — so a search-discovered national team is reachable before the user has logged a match. Clicking a national-team row jumps to `/teams/{id}`, and the team page in turn carries a country chip that links back here, closing the loop.
- **National team is never a club**: `computePlayerStats` and `getPlayerHeader` both filter the `teams` cache for `national=1` before assigning `club`/`clubId`/`clubCrest`. In stats, `recordClub` short-circuits when the team being recorded is national (the player keeps the previous non-national club, or null). In `getPlayerHeader`, the most-recent transfer is the first transfer whose `team_in_id` is **not** national. Without this filter, watching a Norway match would set Erling Haaland's "club" to "Norway" everywhere. The `nationalTeamIds(ids)` helper in `db.ts` returns the set of those flagged national among a given set of team IDs. **Post-compute rescue**: `enrichPlayerStatsWithClub(stats)` in `player-stats.ts` runs after `enrichPlayerStatsWithNationality` on every player-stats call site. It (a) re-verifies the classification of each currently-set `clubId` by calling `nationalTeamIds` again — catching the race where `computePlayerStats` ran before the teams cache had the relevant `national` flag and a national team slipped through into the club column — and clears any such rows; (a′) as a safety net for manual-entry matches (no team_id at all, so `recordClub`'s `clubId != null` guard never fires), clears any stat whose `club` name equals the player's `nationality` name; (b) for players whose club is now null (either because they only had national-team appearances, or because step (a)/(a′) cleared a bad classification), reads their `player_transfers` cache and assigns the most-recent non-national `team_in` as the club. Unseen transfer histories are lazy-fetched via `/transfers?player=X` (bounded to 15/page). Unknown transfer-destination teams get classified via `fetchTeamProfile` (bounded to 10/page). (c) **Season-endpoint fallback** for players whose `/transfers` genuinely has no data — API-Football's transfers coverage is sparse for many women's football and lower-profile men's players (e.g. Leo Østigård, Morten Thorsby, Ingrid Engen, Rafael Leão, Caroline Graham Hansen all return zero transfer rows). `fetchPlayerCurrentTeam(playerId)` hits `/players?id=X&season=Y` across the last 3 seasons (currentYear → –2) and returns the de-duplicated list of every team the player appeared for. The caller then picks the first non-national team and persists it to `players.current_team_id/name/logo/fetched_at` (schema-drift ALTER columns). Must walk all 3 seasons — current season sometimes has only national-team caps (Julian Ryerson season=2026 is just Norway games, but 2025/2024 is Borussia Dortmund), so stopping at the first populated season would return only the national team. Bounded at 8/page, only fires for players where transfers were already fetched (empty response → try the season endpoint). `getPlayerHeader` on `/players/[id]` applies the same fallback for the club chip. **Rate-limit hygiene**: API-Football signals per-minute throttling two ways — HTTP 429, and HTTP 200 with `errors.rateLimit` set. Both `fetchPlayerCurrentTeam` and `fetchPlayerTransfers` throw on either signal rather than silently returning empty, and the callers `enrichPlayerStatsWithClub` and `getPlayerHeader` skip the cache upsert when the fetch throws. Without this, a burst of 8+ parallel fetches that tripped the rate limit would get persisted as "player has no team"/"player has no transfers" permanently, making the club column blank forever even after the limit reset. The stats page also now runs `enrichTeamRecordsWithCountry(teams)` **before** `computePlayerStats`, so the `national` flag is almost always present by the time `recordClub` runs and the rescue step is a no-op in steady state. **Stale-cache refetch**: both `ensureTeamsClassified` (in `player-stats.ts`) and `enrichTeamRecordsWithCountry` (in `team-stats.ts`) treat rows with `national IS NULL` as "needs classifying" and re-fetch them — necessary because the `national` column was added via ALTER TABLE and rows cached before that point have NULL, which `nationalTeamIds` treats as non-national. A v7 `user_version` migration deletes all `national IS NULL` rows on startup so the next enrichment pass rebuilds them with the flag set.
- **Full names — widened unification**: API-Football lineup payloads return abbreviated names ("L. Messi") and `/players/profiles` sometimes does too. The goal is the **name the player is commonly known by** — NOT always `firstname lastname`, because that would turn "Pedri" into "Pedro González López" or "Luke Shaw" into "Luke Paul Hoare Shaw" (API's `lastname` is often the legal full surname). `fetchPlayerProfile` in `football-api.ts` uses `expandAbbreviatedName(name, firstname, lastname)`. When `name` matches the `^[A-Z]\.(...)\s` initial-and-dot pattern, it scans **all words** in `firstname` for one whose first letter matches the abbreviation's initial — `firstname` often contains multiple given names (Harry Maguire's firstname is "Jacob Harry"), and players who go by a middle name (Harry Maguire, many British players) are recovered by this scan ("H. Maguire" + firstname "Jacob Harry" → "Harry" matches "H" → "Harry Maguire"). When there's still no match, `fetchPlayerProfile` falls back to `/players?id=X&season=Y` (trying current season, then prior) which is sourced from per-season squad data and often carries the common name. If that also returns an abbreviation, we store the abbreviation — best-effort and bounded. Non-abbreviated `name` values from profiles pass through unchanged so mononyms / common-usage names are preserved.

`enrichPlayerStatsWithNationality` does **not** retry cached-but-still-abbreviated entries: `fetchPlayerProfile` already runs its full resolution pipeline (profiles → expand → season fallback), so a cached abbreviation is the best we can get and retrying would only burn API budget (at 2-3 reqs per abbreviated player, a retry loop could easily exhaust the 100/day budget). Five cooperating fixes guarantee the full name wins everywhere: (1) `computePlayerStats` runs a post-pass that prefers the cached profile `name` for every resolved `playerId`; (2) orphan stats (still keyed by name, no id resolved) are matched against the full cache via `tryResolveAbbreviatedName` — conservative initial-of-first + last-name match, and only when the match is unambiguous — then re-keyed to `id:{resolvedId}` (merging into any existing id-keyed row); (3) `enrichPlayerStatsWithNationality` upgrades `s.name` from cache-on-read, and **also refetches cached rows whose name still matches `looksAbbreviated`** (covers entries written before the firstname+lastname fix landed — uncached players take budget priority, abbreviated refreshes use the remainder of the 20-per-page fetch budget); (4) right after a fresh `/players/profiles` fetch the full name is propagated into the in-memory stat row so the current page render picks it up; (5) `getPlayerProfile` picks the **longest** seen lineup name across appearances (not the most recent), so the header never regresses to an abbreviated form when at least one appearance carried the full name. `getPlayerHeader` still proactively calls `fetchPlayerProfile` when the cache is empty so single-player pages don't show "Player 123".
- **Stadium tracking**: Matches gained `venue_id INTEGER`, `venue_city TEXT`, `watched_in_person INTEGER DEFAULT 0` (schema-drift ALTERs, no user_version bump needed). Venue id + city thread from API-Football's `fixture.venue.{id,city}` through `MatchSearchResult` → `/fixtures/[externalId]` → `POST /api/matches`. The add-match browse flow stashes them in `sessionStorage:fixture:{id}`; manual entries via `MatchForm` only capture free-text venue and the in-person boolean (so they show up in in-person lists but have no clickable stadium). `/api/matches/[id]/stadium` PUT toggles the flag from `MatchDetailClient`. `getStadiumAggregates()` in db.ts groups by `venue_id` for the Most Watched Stadiums tables (total + in-person variants). `MatchCard` shows an "In person" pill and links the venue text to `/stadiums/{venue_id}` when the id is set. Stadium detail page lives at `/stadiums/[venueId]` with a full-list sibling at `/stadiums/[venueId]/matches`.
- **Coach + referee tracking**: Matches gained `referee_name TEXT`, `home_coach_id INTEGER`, `home_coach_name TEXT`, `away_coach_id INTEGER`, `away_coach_name TEXT` (schema-drift ALTERs). A first-class `coaches` table mirrors the players cache (`id, name, photo, nationality, country_code, fetched_at`). All three signals are pulled from API requests we **already make** during hydration — no new per-match cost. Specifically: `referee_name` from `fixture.referee` on `/fixtures?id=X`; coaches from `lineup.coach` on `/fixtures/lineups`. `saveMatchDetails` writes both the match columns and upserts each coach into the `coaches` cache so search and drill-down pages see them right away (lineup-derived rows have id+name+photo, no nationality — that's lazy-fetched separately). **Match detail page surfaces all three**: venue + city render as a clickable chip in the metadata row of `src/app/matches/[id]/page.tsx`, linking to `/stadiums/{venue_id}` — only when `venue_id` is set, which is why the v10 migration backfills it from the existing `/fixtures?id=X` call; the referee renders as a sibling chip linking to `/referees/{encoded-name}`. Coaches are placed **inside the Lineups card** in `MatchDetailClient.tsx` (above the pitch) via a `CoachBadge` helper — left for home, right for away — so they're visually adjacent to the players they manage. The server page reads coach photos from the `coaches` cache and forwards `homeCoach` / `awayCoach` props (id + name + photo) into the client component. **Referees are name-only on API-Football v3** — there's no id, no `/referees` endpoint, no profile / photo / country. The only signal is `fixture.referee` (free text). Aggregates therefore key by name; the drill-down URL is `/referees/[encoded-name]`. `getRefereeAggregates()` and `searchRefereesCache(q)` group by `referee_name`. Coaches do have ids (`/coachs?id=X` and `/coachs?search=` — note the spelling, that's API-Football's, not ours), so they get full drill-down treatment: photo, nationality chip, W/D/L derived from which side they were on per match. `enrichCoachAggregatesWithNationality` fills nationality lazily, bounded at 15/page-load. **W/D/L for coaches**: `tally(coachId, side, homeScore, awayScore)` in `getCoachAggregates` — equal scores → draw; scoring side win when `side === "home"` and home > away (or `side === "away"` and away > home); otherwise loss. The drill-down `/coaches/[coachId]` reuses `PagedMatchList` with `perspective: { kind: "player", teamId: appearance.teamId }` so W/D/L pills + side highlighting render correctly even though there's no "team" perspective for coaches. **Backfill**: existing api-football matches predate the coach/referee columns, so `user_version=9` flips `details_complete=0` for all such rows. `hydratePendingMatches(5)` (called from `/stats`, `/coaches`, `/referees`) gradually refills them at 15 API requests per visit. Once a row is re-hydrated and saveMatchDetails sees both teams have starters + goals match score, `details_complete` flips back to 1 — coach/referee absence isn't a completeness criterion (the API legitimately returns null for some matches), so empty fields don't trap the row in an infinite retry loop.
- **Universal paginated match lists**: Match/appearance lists throughout the app funnel through a shared `<PagedMatchList items pageSize={n|null} />` wrapper around `WatchedMatchRow`, which takes a `perspective` (`{kind:"team"|"player", teamId}` or `{kind:"neutral"}`) and optional G/A/Y/R extras chips. Default page size is 10 with Prev/Next; see-all routes (`/teams/[id]/matches`, `/players/[id]/appearances`, `/stadiums/[id]/matches`, `/stats/in-person`, etc.) use `pageSize={null}`. Card headers get a "See all →" link via `<SectionHeader title seeAllHref />`. This replaces the per-page bespoke row markup that used to live on the team and player pages.
- **Club history as tenures**: The transfers list on `/players/[id]` is rendered via `buildPlayerTenures(transfers, currentClubId)` — one row per club spell (start year – end year), Loan pill when `type` contains "loan" (API's `type` field: "Loan", "Free", "N/A", etc.), "present" for the player's current club (the one matching `PlayerHeader.clubId`). National-team rows are filtered out (they belong on the nationality chip). Consecutive spells at the same club are **not** collapsed — a return from a loan is its own tenure, which keeps the timeline legible for back-to-back loan spells.
- **Symmetrical match/appearance rows**: `WatchedMatchRow` renders W/D/L whenever a side is present (team page = `{kind:"team", teamId}`; player page = `{kind:"player", teamId: appearance.teamId}`), crests + team-name links + clickable score + minutes pill + optional G/A/Y/R extras + "In person" pill + date link. Team profile `TeamMatchAppearance` now carries `watchedInPerson`; player profile `PlayerMatchAppearance` now carries both `teamId` (the side the player was on, so W/D/L renders correctly) and `watchedInPerson`. The home feed's `MatchCard` is the only deliberately different layout (bigger card for the feed); it still shows the In-person pill beside the competition badge.
- **Global search (cache + live API merge)**: `<GlobalSearch>` lives in the navbar (⌘K-focusable, debounced 250 ms). On every keystroke it hits `GET /api/search?q=…`, which runs six LIKE queries against the local `teams` / `players` / `competitions` / `matches.venue` / `coaches` / `matches.referee_name` caches and — when `q.length >= 3` — also fans out five `Promise.allSettled` calls to API-Football (`/teams?search=`, `/players/profiles?search=`, `/leagues?search=`, `/venues?search=`, `/coachs?search=`). Cache and live results are merged + deduped by id, capped at 6 per group. Each row carries a `source: "cache" | "api"` flag; live-only rows show a small "new" pill so the user can tell what's already in their data. Live results are written back to the same cache tables (`upsertTeam` / `upsertPlayer` / `upsertCompetition` / `upsertCoach`), so the next search for the same term is instant and free. The min-3-chars threshold is API-Football's own constraint; below it we still serve cache hits but skip the API entirely. **Referees never hit the live API** — there's no API-Football endpoint for them — so the Referees group only ever shows cache hits sourced from `matches.referee_name`. **API budget**: a fully-fired live search costs 5 daily requests (was 4 before coaches); combined with the 250 ms debounce + abort on each new keystroke, a typical user session burns ~5–15 requests against the 100/day cap. The dropdown links each row to its existing drill-down page (`/teams/[id]`, `/players/[id]`, `/competitions/[id]`, `/countries/[code]`, `/stadiums/[venueId]`, `/coaches/[id]`, `/referees/[encoded-name]`) — no new detail pages were built for the search itself. **Countries** are a separate group sourced from the static `searchCountries(q)` helper in `country-codes.ts` (substring match against the canonical name list, prefix-match ranks first). No cache, no API call — purely static — so they have `source: "static"` and never show the "new" pill. Type-only `import type { SearchResponse } from "@/app/api/search/route"` keeps the server-only `db.ts` and `football-api.ts` from leaking into the client bundle.
